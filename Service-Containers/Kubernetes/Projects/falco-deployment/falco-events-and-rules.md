# Falco Events & Rules

**Note:** If you have not installed Falco yet, I'd advise you to do so. That documentation is also on GitHub.

---

## Falco Events

### Introduction

- Falco evaluates streams of events against a set of rules to detect any abnormal behavior. These event resources come through different event sources. These event sources define the origin, nature, and the format of streamed events.

- Each event source operates in an isolated thread where events are generated by Falco's rule engine. Rules are partitioned by event source, meaning each rule applies to a specific source and is triggered by events just from that source.

- In simple terms, event sources are different places where Falco gets information about what's happening on the system, so it will listen to these events to watch for suspicious activity.

---

## Managing Event Sources

Falco gives you a ton of flexibility when it comes to event sources and what sources you'd like to use. This is possible with the following commands:
```bash
--enable-source
```

and
```bash
--disable-source
```

### Default Event Sources

- **Syscall source** is on by default and built into Falco
- **k8s_audit** needs to be manually configured; for it to be enabled the k8saudit plugin needs to be installed and configured

### Example: Enable Specific Sources

For example, if you wanted to enable JUST k8s audit and syscall sources, you would run the command below:
```bash
falco --enable-source=syscall --enable-source=k8s_audit
```

### Example: Disable Specific Sources

Now let's say you wanted to do the opposite so you can tailor event monitoring to your needs. You would run the command:
```bash
falco --disable-source=syscall --disable-source=k8s_audit
```

---

## Using a Source Without a Driver

By default, Falco enables the syscall source and uses a kernel driver to capture events. However, in some scenarios you would want to generate syscall events without the driver (like if you are testing a plugin). To do this and still use syscall, run the command:
```bash
falco -o engine.kind=nodriver
```

## Falco Rules

### Introduction

Falco has a rules file in YAML. It contains 3 types of elements:

1. **Rules**: A condition where an alert should be generated. The rule goes alongside a descriptive output string sent with the alert.

2. **Macros**: Condition snippets that can be re-used inside rules and other macros. They provide a way to name common patterns and filter out any redundancies within the rules. They're essentially little building blocks made to define common patterns once. They are then referenced in multiple rules to avoid those said redundancies and repetition.

3. **Lists**: A collection of items either in rules, macros, or nested in other lists. Lists can't be parsed as filtering expressions, so lists are just collecting values.

### Optional Versioning Elements

Falco can also optionally contain two elements related to versioning:

- **required_engine_version**: Used to track compatibility between rules content and the Falco engine version
- **required_plugin_version**: Used to track compatibility between rules content and plugin versions

**Note:** Falco has a rules repo to make some rules easy to install and for some solid examples.

---

## Basics of Falco Rules

A Rule is a YAML object, part of the rules file. It contains at least the following fields:
```yaml
- rule: shell_in_container
  desc: notice shell activity within a container
  condition: >
    (evt.type in (execve, execveat)) and
    container.id != host and
    (proc.name = bash or
    proc.name = ksh)
  output: >
    shell in a container |
    user=%user.name container_id=%container.id container_name=%container.name
    shell=%proc.name parent=%proc.pname cmdline=%proc.cmdline
  priority: WARNING
```

---

## Understanding Conditions

**Conditions** are boolean expressions that check if a specific field value in an event matches certain criteria to trigger an alert.

### Example 1: Basic Shell Detection

For example, if you wanted a condition that alerts Falco whenever a bash shell is run inside a container, you would add the condition below:
```yaml
container.id != host and proc.name = bash
```

**Breaking it down:**
- **First clause**: `container.id != host` - It checks if the event happened in a container by checking if the event did not happen in the host machine. By process of elimination, it happened in a container.
- **Second clause**: `proc.name = bash` - It checks that the name of the process is bash, which means the process ran in bash.

### Example 2: Shell Spawn Detection

Another example: if you want to be alerted only for each shell spawn in a container, add these event types to the condition:
```yaml
(evt.type in (execve, execveat)) and container.id != host and proc.name = bash
```

---

## Complete Rule Example

A complete rule using the condition(s) we just made would be:
```yaml
- rule: shell_in_container
  desc: notice shell activity within a container
  condition: >
    (evt.type in (execve, execveat)) and
    container.id != host and
    (proc.name = bash or
    proc.name = ksh)
  output: >
    shell in a container |
    user=%user.name container_id=%container.id container_name=%container.name
    shell=%proc.name parent=%proc.pname cmdline=%proc.cmdline
  priority: WARNING
```

### Breaking Down the Rule

- `rule: shell_in_container`: Names the rule
- `desc: notice shell activity within a container`: Describes the rule
- `condition: >`: Starts the condition block (the `>` means multiline text)
- The condition checks for:
  - Event types `execve` or `execveat` (shell execution events)
  - Container environment (not the host)
  - Process name is `bash` or `ksh`
- `output: >`: Defines the alert message format with variables
- `priority: WARNING`: Sets the alert severity level

---

## Rule Fields Explanation

### Required Fields

- **rule**: The unique name/identifier for the rule
- **desc**: A description of what the rule detects
- **condition**: The boolean expression that triggers the alert
- **output**: The alert message format (can include variables)
- **priority**: The severity level (e.g., WARNING, ERROR, CRITICAL)

### Condition Operators

Common operators used in conditions:
- `=`: Equals
- `!=`: Not equals
- `in`: Checks if value is in a list
- `and`: Logical AND
- `or`: Logical OR

### Output Variables

Output strings can include variables to provide context:
- `%user.name`: Username
- `%container.id`: Container ID
- `%container.name`: Container name
- `%proc.name`: Process name
- `%proc.pname`: Parent process name
- `%proc.cmdline`: Command line arguments
